# v0.5 Home Assistant validation

## What changed

- Added `qbittorrent_enhanced.get_torrents` as a response-only Home Assistant action.
- The action returns coordinator-owned normalized torrent data; the Lovelace card therefore has no qBittorrent credentials or direct HTTP polling path.
- Replaced invalid-looking `object` selectors for hashes/tags with text selectors pending a richer UI selector design.
- Removed `strings.json`: current Home Assistant documentation says custom integrations should ship explicit files under `translations/` instead.

## Required runtime validation

The artifact is still a custom-integration scaffold, not a claim of runtime certification. Install it in a disposable Home Assistant 2026.x instance and verify:

1. Config flow creates an entry and rejects duplicate host/entry identity.
2. `qbittorrent_enhanced.get_torrents` appears in Developer Tools → Actions.
3. Calling `get_torrents` with `entry_id` returns JSON-serializable `server` and `torrents` data.
4. Torrent actions refresh the coordinator and the returned torrent list reflects the change.
5. API-key auth works against qBittorrent 5.2.x; username/password fallback works where supported.
6. Diagnostics contain no API key or password.
7. The built-in `qbittorrent` integration is not simultaneously configured, because this custom component intentionally overrides the same domain.

## Current design decision

The frontend data path is:

`Lovelace card → Home Assistant action response → coordinator → qBittorrent API`

No qBittorrent HTTP request is made by the card. This follows the project baseline requirement and uses Home Assistant's response-data action mechanism, which is explicitly intended for streams/collections of objects that do not fit entity state.
